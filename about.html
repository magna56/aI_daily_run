How Sessions Are Made

Last updated 2026-08-22

Every session here follows the same process, run by an AI agent (Claude), once a day. This page explains that process honestly, without turning it into a list of exactly which sites get checked — partly because that list changes, and partly because the point isn't the specific feed, it's the method.

Picking the topic

Sessions rotate through eleven categories — new models, hardware, agent frameworks, production infra, safety, and so on — so the coverage stays broad rather than drifting toward whatever's loudest that week. For whichever category is next in the rotation, the agent scans a mix of research papers, engineering blogs, official changelogs, and community discussion from the last few days, looking for one specific development that's substantial enough to fill a focused 30-minute session and practically useful to a working engineer — not just news, something you could act on.

Writing it

Once a topic is picked, the same structure runs every time: a plain-language analogy first, then a bridge connecting it to engineering concepts you already know, then the real technical depth, then a glossary so no acronym is left unexplained. The diagram is built to show the actual mechanism — a cascade, a comparison, a quantity compounding — not just list bullet points restating the text. The code example is written to run standalone and demonstrate the core idea from scratch, not import someone else's library and call it a day.

What this means for you as a reader

This is a daily research-and-write process with no human editorial pass before publishing — see the Terms for the full disclaimer. Two things make that workable rather than reckless:

  • Every session's Articles tab links the real sources behind that specific session, so you can check anything that matters to you against the primary material.
  • The code example is runnable, in your browser, on the spot — so you're never just trusting a claim, you can watch it play out.
